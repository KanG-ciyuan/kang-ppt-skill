# Narrative And Evidence

## Communication Job

Before choosing slide count or layouts, state:

```text
communication_job = By the end, [audience] should [outcome] because [central takeaway].
```

The outcome can be understanding, approval, a decision, a trial, a discussion, or a concrete action. Do not force persuasion onto a reference or teaching deck.

## Narrative

- Choose a cumulative arc appropriate to the job: problem -> cause -> response -> evidence -> action; question -> analysis -> answer; current -> change -> future; or another defensible sequence.
- Give each slide one narrative job and one primary claim.
- Use takeaway titles that a presenter could naturally say aloud.
- Make each slide answer a question created by the prior slide or create the need for the next.
- An agenda, feature inventory, or chronological dump is not a narrative by itself.
- Keep audience-facing copy free of prompts, production notes, timing scaffolds, model reasoning, and internal quality checks.

## Evidence Ledger

| State | Allowed use |
|---|---|
| `verified` | current inspected source or runtime evidence; may be stated within its actual scope |
| `historical` | dated evidence; state the date or historical boundary when material |
| `to_verify` | unresolved; remove, qualify, or show only as an explicit gap |
| `do_not_publish` | secret, private, irrelevant, unsafe, or prohibited; never place in the deck |

Confidence, popularity, visual polish, and repetition do not turn an unsupported statement into evidence.

## Claims And Sources

- Never invent metrics, customers, quotes, testimonials, screenshots, outcomes, ratings, research, or performance claims.
- For missing claims, use `remove_qualify_or_to_verify`: remove them, narrow the language, or visibly mark the unresolved status when the audience must know.
- Do not turn planned work into a completed result.
- Keep externally sourced non-trivial claims and assets traceable in speaker-note source blocks as required by `Presentations`.
- Preserve source semantics: installs are not ratings, historical test results are not current runtime proof, and a prototype is not production deployment.

## Customer Proposals

Do not promise price, delivery date, security, availability, integration success, performance, savings, or conversion without authorized evidence. Prefer a bounded trial or requirements discussion when commercial proof is missing.
